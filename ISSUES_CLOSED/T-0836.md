# T-0836 — Dispatch queued jobs to the worker for their type

## Report

The job queue (T-0010) supervises one worker, `run-tenant.ps1`, for every envelope. Envelopes also
carry `remediation`, `standards`, `drift`, `baseline`, `backup`, and `report` job types, whose
workers take different arguments: `plan-remediation.ps1` and `apply-remediation.ps1` read the
envelope itself as `-JobFile` plus `-OutputFolder`, while the supervisor passes `-ContextFile`.
Enqueueing any of them today would run an assessment instead.

T-0824 therefore mounts remediation plan, apply, and verify and schedule run-now with ports that refuse
with 501 `jobs.dispatch_unavailable`. Also missing on these paths:

- Nothing stores a worker's output: remediation plans and action results are never written to the
  remediation tables (compare T-0833 for findings).
- Scheduled runs create no run record, and the envelope's `context.json` is written only for
  assessment runs (T-0821's run queue).
- Nothing starts the scheduler tick (`scheduler/tick.ts`), so due schedules never run.
- The queue persists only the envelope payload; schedule history finds a schedule's jobs by its
  `schedules/<id>/` refs.

## Acceptance

- [x] A decision records how job types map to workers and their arguments.
- [x] Remediation plan jobs run their worker, and their results are stored and served by the remediation routes. (Apply split to T-0838.)
- [ ] ~~Schedule run-now and the tick enqueue runnable jobs with run records; history reflects them.~~ Split to T-0840.
- [ ] ~~The 501 ports in `adapters/automation.ts` are removed.~~ Plan's is removed; apply/verify (T-0838, T-0839) and schedules (T-0840) keep theirs until their tickets land.

## Resolution

Split on scope review: this ticket delivers the dispatcher and remediation plan jobs end to end.
Apply (T-0838), verify (T-0839), and schedules (T-0840) each need pieces of their own, so they
are filed separately.

- **Dispatch decision:** one queue, one runner per job type (`jobs/dispatch.ts`,
  `createJobDispatcher`). A type with no runner fails its job with `jobs.no_worker`, never
  starting the wrong worker. Each runner supervises its own entrypoint with its own arguments
  (`superviseJob` gained a `buildArgs` option). Result handling wraps the dispatcher per type:
  findings for assessments (T-0833), plans for remediation. Remediation envelopes carry
  `payload.operation` (`plan` | `apply` | `verify`).
- **Plan jobs:** the queue port writes the envelope as `job.json` (no credential: planning makes
  no tenant calls) and the run's stored findings as `findings.json` into the job's folder. The
  runner runs `plan-remediation.ps1 -JobFile -OutputFolder -FindingsFile`. On success,
  `withRemediationPlanIngestion` stores the plan, its actions, and its manual instructions from
  `remediation-plan.json` under the plan id the route returned. A retry does not fail on an
  already-stored plan, and missing or malformed output fails the job with
  `remediation.output_unreadable`. The mapping is in the db package (`remediationPlanFromWorkerOutput`)
  because of the BFF's thin-backend guard. Its fixture is real `plan-remediation.ps1` output.
- **Bugs fixed on the way:**
  - Remediation envelopes used the assessment run's folder as their output folder, so a
    job's `result.json` would overwrite the assessment's. Each job now gets
    `remediation/<tenantId>/<jobId>`.
  - The plan route returned a `planId` it never sent to the worker, so the plan could never
    be found under it.
  - The web page sends only `tenantId`. The empty `runId` failed envelope validation, so
    planning from the portal could never work. The route now uses the tenant's latest
    finished run, or returns 409 `remediation.no_run` if there is none.
  - The plan worker passed no caller to `Test-RemediationGate`, so every action was
    `rbac-denied`. The route now sends `caller: { canApply, tenantScope }` and the worker
    rebuilds the gate's caller shape. The gate runs in strict mode and `-AsHashtable` keys
    are case-sensitive, so passing the payload through as-is failed.
  - The latest-run lookup (reports and remediation) could pick a parent run, which holds no
    results of its own. It now skips runs that have children.
  - `createdBy` was always empty for the portal's callers. The remediation routes now read the
    caller's `userId`.
- **Web:** the plan appears only when its job finishes, so the remediation page now polls
  (`waitForRemediationPlan`) instead of failing on the 404.
- Plans made by portal callers now reach the admin allowlist gate (`not-allowlisted` until an
  admin allowlists checks), as intended. Not verified against a live tenant.
