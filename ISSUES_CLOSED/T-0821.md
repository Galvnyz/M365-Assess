# T-0821 — Mount the Runs and progress routes on real storage

## Report

The EPIC-001, EPIC-003 route modules (runs.ts, runs-actions.ts, runs-artifacts.ts, runs-create.ts, runs-detail.ts, runs-events.ts, runs-list.ts, health.ts sources) take interfaces with no implementation: `RunStore`, `RunCreateStore`, `RunsDetailStore`, `RunListStore`, `RunsActionsStore`, `RunsArtifactsStore`, `RunEventsStore`, the `RunQueue` (T-0010 `JobQueue` with `createSupervisorRunner`), and the `ProgressEventHub`. The
`@m365-assess/db` repositories hold the data but expose different method shapes, and the BFF does
not yet depend on that package.

Add `@m365-assess/db` as a BFF dependency if it is not already present, write adapters under
`portal/bff/src/adapters/` that implement each interface on top of the db repositories (or the BFF's
own repositories where the entity lives there), and mount the routes in `app.ts` with the T-0817
authorizer, caller resolution, and audit sink. Adapters translate shapes only — no domain logic
(ADR-0014 thin BFF).

## Acceptance

- [x] Every EPIC-001, EPIC-003 route module is mounted on adapters over persistent storage (no in-memory fakes).
- [x] Each adapter has a test against a real in-memory SQLite database.
- [x] An app-level test reaches at least one read and one write route per epic through the server with the authorizer applied.
- [x] No file outside `scope` is modified.

## Resolution

- `adapters/runs.ts`: one run store implements the create, list, detail, actions, artifacts, and
  events stores plus the progress hub's run/section writes over the db repository. Sections are
  kept to one row per run section as progress arrives. The job queue persists through the jobs
  table (`createJobPersistence`), and tenant-group runs resolve members through the EPIC-002 group
  store (`resolveMembers` is now exported from `routes/tenant-groups.ts`).
- The run queue writes each tenant run's `context.json` (tenant, certificate-thumbprint credential,
  sections, output folder) under the artifact root before enqueueing; nothing wrote it before, so no
  run could start. Runs whose tenant has no credential, or a client-secret/PFX one, fail at once with
  the reason (T-0827 now covers resolving secrets in `run-tenant.ps1`).
- `superviseJob` takes a `storageRoot`: the worker runs there and `result.json` is read from there,
  since envelope refs are relative.
- Parent runs now roll up from their children (`domain/runs/run-rollup.ts`): queued, running, then
  succeeded/failed/cancelled, or partial when children differ. Every run has a parent, which
  otherwise stayed queued forever.
- Mounted the EPIC-003 modules. `routes/runs.ts` (EPIC-001) is superseded on every path and not
  mounted; T-0834 removes it.
- The routes' `readBody` seam gets the server-parsed body re-serialised; without it they ignored the
  request body.
- `health.ts` was already mounted (T-0817).
- Follow-ups: T-0832 (the server cannot stream, so progress is delivered in 25-second batches),
  T-0833 (nothing turns run output into findings or summary counts), T-0834.
