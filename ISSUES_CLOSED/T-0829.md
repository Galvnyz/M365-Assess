# T-0829 — Load a policy's settings into the editor

## Report

The T-0304 editor pre-fills existing policies from the list API's `settingsSummary`, but the list
worker never sets that field (settings-catalog settings are a separate Graph read), so editing or
cloning a policy starts from empty settings and a save would drop them. T-0820 added a single-policy
detail read to the worker (`Get-IntunePolicyDetail`, used by compare) and a provider for it.

Add `GET /v1/tenants/:tenantId/intune/:kind/:policyId` on that provider (Read permission, registered),
have `getIntunePolicy` in `intuneApi.ts` call it instead of paging the list, and pre-fill the editor
from the returned body (settings-catalog `settings` for configuration, properties for compliance).

## Acceptance

- [x] The detail route returns one policy's body and assignments, 404 when missing.
- [x] The editor pre-fills an existing policy's settings from it; a clone does too.
- [x] Tests cover the route and the editor pre-fill and fail without the change.
- [x] No file outside `scope` is modified.

## Resolution

- `GET /v1/tenants/:tenantId/intune/:kind/:policyId` (`INTUNE_POLICY_PATH`, Read permission, registered)
  on an optional `getPolicy` provider method backed by the worker's `Get-IntunePolicyDetail`; 404 when
  missing, 501 without a detail-capable provider.
- `getIntunePolicy` reads that route; `editableSettingsFromDetail` flattens settings-catalog entries to
  settingDefinitionId -> value (choice `_1`/`_0` -> true/false) and keeps compliance properties minus
  identity fields; `assignmentsFromDetail` maps Graph targets to the portal shape.
- Also fixed (scope addition, found here): the Intune policy list/CRUD routes and three Conditional
  Access routes (`ca-coverage`, `ca-named-locations`, `ca-report-only`) returned `JSON.stringify(...)`
  as the body, which the server encodes again, so clients received a JSON string instead of an object.
