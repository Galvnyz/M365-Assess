# T-0833 — Record findings and summary counts from a finished run

## Report

A run's worker writes the assessment's artifacts (HTML, XLSX, JSON, CSVs) and a result envelope
listing them. Nothing reads those artifacts back: no code calls `createFinding`, so
`GET /v1/runs/:runId/results` always returns no findings, and `summaryCounts` stays empty for every
run (the detail route's parent aggregation sums empty counts). Dashboards and drift that read
findings see nothing from portal runs.

When a job succeeds, read the assessment's machine-readable output from the run's artifact folder,
map each check to a `Finding` (checkId, status, severity, category, collector, current and
recommended values, framework refs), store them, and set the run's `summaryCounts` by status.
This is the one place a result is interpreted, so keep the mapping in `domain/runs/` and the
file reading in the adapter.

## Acceptance

- [x] A succeeded run's findings are stored from its output, and `GET /v1/runs/:runId/results` returns them.
- [x] The run's `summaryCounts` reflect its findings by status; the parent aggregates its children.
- [x] A run whose output is missing or unreadable is marked with the reason, not silently empty.
- [x] Tests use a real assessment output fixture.

## Resolution

- Source decision: the assessment's bridge export, `_Assessment*.json` (`Export-AssessmentBridgeJson`),
  which is its one machine-readable list of check results. The per-collector CSVs would mean
  re-implementing the report pipeline's enrichment (severity, frameworks) in the portal.
- The export gained `category`, `setting`, `recommendedValue`, `section`, and `collector` per finding
  (additive; M365-Remediate ignores them). Writing the fixture exposed two export bugs, now fixed: a
  finding mapped to exactly one framework was written as a bare string instead of an array, and
  framework and domain-summary key order varied between processes. CHANGELOG updated under
  Unreleased. The export had no Pester tests; it now has six, one of which regenerates the portal
  fixture and fails if the committed copy drifts.
- The mapping lives in the db package (`findingsFromAssessmentExport`), not `domain/runs/` as scoped:
  the BFF's thin-backend guard forbids the check identifier the export is keyed by. The db also gained
  `replaceRunFindings`, a transactional swap so re-ingesting a run does not duplicate findings, and
  findings now list in insertion order.
- `withFindingsIngestion` wraps the queue's worker runner: after a succeeded assessment job it reads
  the export named in the result's artifact refs (confined to the run folder), stores the findings,
  and sets `summaryCounts` by status, all before the queue reports the job finished. A missing or
  unreadable export, or a finding with no check or an unknown status, fails the run with
  `run.output_unreadable` and the reason in `summaryCounts.error`; a failed worker's error message is
  kept there too. The parent run's detail already sums its children's counts.
- Not verified against a live tenant (none available); the fixture is produced by the real export
  function over synthetic rows.
