# T-0261 — Groups read API: list, search, filter, and type discrimination

## Report

EPIC-014 SPEC.md §3.1 defines the **Groups** table columns (Name · Type · Membership count ·
Owners · Hidden from GAL · Delivery mgmt · Dynamic rule) and filters (type, hidden, dynamic,
membership size); §6 fixes `GET /v1/tenants/{id}/groups` as list/search. §7 requires RBAC
`groups.read` and Graph `Group.Read.All`; groups are read live from Graph and never mirrored
(§5).

Deliver a read-only worker handler `Get-Groups.ps1` in the `M365Portal.Workers` module plus a
thin `get-groups.ps1` entrypoint that rehydrates the EPIC-001 `RunContext` and emits a result
envelope (T-0006, T-0007), and the BFF route `groups-list.ts` behind the built-in RBAC seam
(T-0013). The handler must discriminate group type (unified/M365, security, mail-enabled
security, distribution, dynamic) as fixed by SPEC §11.1 — **M365, security, and distribution
groups ship first**, other types later — and expose the derived membership count, owner count,
`hiddenFromAddressListsEnabled`, delivery-management flag, and dynamic membership rule so the UI
can render without N+1 calls. Search and filter parameters are validated and applied
server-side with cursor pagination (EPIC-001 §6). This ticket must add no tenant writes.

## Acceptance

- [x] `GET /v1/tenants/{id}/groups` lists groups with type, membership/owner counts, GAL/delivery flags, and dynamic rule.
- [x] Type, hidden, dynamic, and membership-size filters and a search term are applied and covered by tests.
- [x] The worker is read-only; the guard test in T-0015 still passes.
- [x] A test covers the route and handler and fails without them.
- [x] No file outside `scope` is modified.
