# T-0824 — Mount the Remediation, schedules, and scripts routes on real storage

## Report

The EPIC-006, EPIC-007 route modules (remediation.ts, schedules.ts, scripts.ts) take interfaces with no implementation: `RemediationPlanStore`, `RemediationQueue`, `ScheduleStore`, `ScheduleHistoryStore`, `ScheduleRunQueue`, `CustomScriptStore`, and the `ScriptSandbox` over the T-0126 sandboxed worker. The
`@m365-assess/db` repositories hold the data but expose different method shapes, and the BFF does
not yet depend on that package.

Add `@m365-assess/db` as a BFF dependency if it is not already present, write adapters under
`portal/bff/src/adapters/` that implement each interface on top of the db repositories (or the BFF's
own repositories where the entity lives there), and mount the routes in `app.ts` with the T-0817
authorizer, caller resolution, and audit sink. Adapters translate shapes only — no domain logic
(ADR-0014 thin BFF).

## Acceptance

- [x] Every EPIC-006, EPIC-007 route module is mounted on adapters over persistent storage (no in-memory fakes).
- [x] Each adapter has a test against a real in-memory SQLite database.
- [x] An app-level test reaches at least one read and one write route per epic through the server with the authorizer applied.
- [x] No file outside `scope` is modified.

## Resolution

- Schedules and custom scripts persist through the db repositories (now exported), which already
  match the route stores. Remediation reads go through `createRemediationStore`.
- Schedule history comes from the jobs table: the queue stores only the envelope payload, so a
  schedule's jobs are found by their `schedules/<id>/` refs.
- Running things is not wired: the job queue only supervises `run-tenant.ps1`, so remediation and
  scheduled jobs would run the wrong worker, and the script sandbox has no entrypoint. Remediation
  plan/apply/verify, schedule run-now, and script runs refuse with 501. Filed T-0836 (job dispatch)
  and T-0837 (script sandbox).
- Scope additions: the BFF's thin-layer guard rejects the collector identifier the db uses for a
  remediation action's check reference, so the db package now exports views that rename it
  (`toRemediationActionView`, `toManualInstructionView`), plus `getRemediationAction`, which the
  verify route needs.
