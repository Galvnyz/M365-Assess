# T-0206 — Offboarding run worker with per-step progress and re-run

## Report

EPIC-011 SPEC.md §4.4 (US-5): on confirm, a job runs steps **sequentially in the tenant's child
process**; each step is individually recorded and **re-runnable**; progress streams to the UI; a
failed step is surfaced with a re-run action rather than silently skipped. Mailbox permission
grants use the chosen access mode (full/send-as/send-on-behalf, automap). Destructive steps
(delete user, wipe device) require explicit confirmation.

Add the BFF `POST /v1/tenants/{id}/offboarding`,
`GET /v1/tenants/{id}/offboarding/{jobId}`, and
`POST /v1/offboarding/{jobId}/steps/{order}/rerun` routes; implement `Invoke-UserOffboarding.ps1`
plus the `invoke-user-offboarding.ps1` entrypoint that rehydrates the plan and executes steps in
order through the EPIC-006 apply/audit path (T-0108), and `Rerun-OffboardingStep.ps1` for a
single-step re-run. Progress uses the EPIC-001 progress-event contract; extend `portal.v1.yaml`.
Depends on the EPIC-002 tenant credential model for tenant selection at runtime (not yet
authored).

## Acceptance

- [x] Confirming an offboarding job runs its steps sequentially and records each step's state/result/error.
- [x] A failed step is surfaced with a re-run action; the job does not silently continue past a destructive failure.
- [x] Re-running a step does not re-execute already-applied steps of the job.
- [x] Mailbox permission grants honor the selected access mode and are verified after apply.
- [x] A test covers the change and fails without it.
- [x] No file outside `scope` is modified.
