# T-0838 — Run remediation apply jobs and store their results

## Report

T-0836 dispatches remediation plan jobs. Apply (`POST /v1/remediation/plans/:planId/apply`) still refuses with 501
`jobs.dispatch_unavailable` in `createRemediationQueue`, because apply needs pieces plan does not:

- `apply-remediation.ps1` signs in with `Connect-WorkerTenant -JobFile`, so its `job.json` must carry the
  tenant's credential block (`toCredentialBlock`), like the feature workers. That includes the T-0827 limit
  on secret-backed credentials.
- It reads the plan from `-PlanFile` (default: `remediation-plan.json` in its own output folder). The plan
  job's output lives in the plan job's folder, so the runner must pass that path or write the stored plan.
- Its `remediation-apply.json` results must update each action (`updateRemediationAction`: state,
  before/after, appliedAt/appliedBy, error), which the history and plan routes serve.
- The apply route's Idempotency-Key store is in memory, so a replay after a restart enqueues a second apply.

## Acceptance

- [ ] An apply job runs `apply-remediation.ps1` with the tenant's credential block and the stored plan.
- [ ] Each applied action's state and result are stored and served by the plan and history routes.
- [ ] Dry runs change no action state.
- [ ] Idempotency survives a restart, or the limitation is documented.
