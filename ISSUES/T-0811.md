# T-0811 — BFF composition root: mount routes and back them with workers

## Report

`portal/bff/src/index.ts` calls `buildServer()` with no `routes`, and none of the 76
`portal/bff/src/routes/*` factories (`createIntuneTemplateRoutes`, `createCaPoliciesRoute`,
`createIntuneCompareRoute`, …) is imported outside its own file and tests. Every feature
endpoint delivered by the portal epics is therefore unreachable. Each factory takes injected
dependencies — a repository (in-memory/SQLite), a provider that runs a PowerShell worker,
`resolveCaller`, an authorizer, and often `recordAudit` — and nothing constructs them.

Build the composition root:

1. `app.ts` constructs the SQLite repositories, the auth `resolveCaller`, the permission-aware
   authorizers, and an audit sink, then returns the full route list for `buildServer`.
2. `providers/` implements the provider interfaces on top of `jobs/supervisor.ts`
   (`superviseJob` / `createSupervisorRunner`): write the T-0007 job envelope, run the named
   worker entrypoint (e.g. `portal/workers/deploy-intune-template.ps1`), parse its JSON.
3. Register every mounted endpoint in `rbac/permissions.ts`; the existing
   "resolves exactly one permission for every mounted endpoint" test enforces completeness.

This is too large for one dispatch. Scope review should split it — for example one ticket for
the root plus the job-backed provider seam, then one per epic mounting its routes.

## Acceptance

- [ ] `index.ts` serves the feature routes through `app.ts`.
- [ ] Worker-backed providers run workers through the job supervisor, not ad-hoc spawns.
- [ ] Every mounted endpoint resolves exactly one permission in `rbac/permissions.ts`.
- [ ] A test mounts the app and exercises at least one route per epic end to end with a fake supervisor.
- [ ] No file outside `scope` is modified.
