# T-0827 — Persistent backend for client-secret and PFX credentials

## Report

EPIC-002 stores only a `secretRef` in the database; secret material lives behind the
`CredentialStore` contract (`portal/bff/src/credentials/store.ts`), and workers resolve it in the
child process through `Resolve-TenantCredential -CredentialStore { param($SecretRef) ... }`. The only
implementation is `createInMemoryCredentialStore`, so client-secret and PFX credentials are lost on
restart and no worker can read them. Certificate-thumbprint credentials need no material and are
unaffected.

**Decision needed before implementation:** where material lives — OS keystore (Windows
Credential Manager / macOS Keychain / libsecret), a DPAPI- or age-encrypted file under
`storagePath`, or an external vault (Azure Key Vault). The choice sets the threat model, how the
worker child reads material without the parent handing it over, and how set/rotate/expiry
(T-0023) behave.

## Acceptance

- [ ] The chosen backend implements `CredentialStore` persistently and passes the existing store contract tests.
- [ ] Workers resolve client-secret and PFX material through it inside the child process only.
- [ ] Assessment runs accept client-secret and PFX credentials: `run-tenant.ps1` resolves the run's
  `credentialRef` in the child, and `createRunQueue` (T-0821) stops failing those runs up front.
- [ ] Material never appears in logs, responses, job files, or error messages.
- [ ] No file outside `scope` is modified.
